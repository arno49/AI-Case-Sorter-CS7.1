# Internal API and Events

## Scope and contract ownership

This is the private `cs71d` API over `/run/cs71/cs71d.sock`, consumed by the SvelteKit BFF. It is not browser- or LAN-addressable. The OpenAPI document is the source contract for `/v1`; generated TypeScript types/client are checked into or regenerated by the build from that contract. Arduino v2 wire frames remain governed by [PROTOCOL_V2.md](../../ArduinoCode/PROTOCOL_V2.md), not this API.

| Identifier | Owner | Scope |
| --- | --- | --- |
| `operation_id` | `cs71d` | UUID durable lifecycle/audit identifier. |
| daemon `event_id` | `cs71d` | Monotonic SSE cursor, unique in daemon event retention scope. |
| protocol `request_id` | firmware protocol | v2 session correlation; numeric, wraps/session-scoped, never exposed as durable business identity. |
| snapshot generation | `cs71d` | Monotonic immutable machine-view version used for optimistic concurrency. |

## Request rules

All JSON uses RFC 3339 UTC timestamps, lower_snake_case JSON fields, UTF-8 and explicit schema `api_version`. State-changing requests require all of: BFF service authentication on the socket, propagated authenticated actor metadata, `Idempotency-Key`, `If-Match-Generation`, and `X-Deadline-Ms`. For ordinary commands, `If-Match-Generation` is an exact observed generation. Priority stop also requires the header but may use `*` to request an attempt despite stale/uncertain state; its outcome is still trusted, failed, or `UNCERTAIN`, never assumed. Request bodies are size-limited and command names/slots are allow-listed.

Responses use `X-Request-ID` for transport diagnostics and return `ETag: "generation:<n>"` for snapshots. The daemon must never trust a caller-supplied role; SvelteKit authorizes browser identity and daemon validates the restricted BFF identity/metadata format.

## Resources

| Method | Resource | Response |
| --- | --- | --- |
| `GET` | `/v1/health/live` | process liveness only; 200 does not assert controller readiness. |
| `GET` | `/v1/health/ready` | readiness, connection/fault reason and generation. |
| `GET` | `/v1/snapshot` | complete immutable `MachineSnapshot`. |
| `GET` | `/v1/events` | SSE event stream. |
| `POST` | `/v1/session/connect` | 202 `OperationAccepted`. |
| `POST` | `/v1/session/recover` | 202 `OperationAccepted`; explicit confirmation field required. |
| `POST` | `/v1/machine/stop` | 202 `OperationAccepted` for priority software stop. |
| `POST` | `/v1/operations/home` | 202 for feeder, sorter or both. |
| `POST` | `/v1/operations/sort` | 202 for a capability-validated slot. |
| `POST` | `/v1/operations/feed` | 202 for a capability-validated feed operation; unavailable until the firmware feed lifecycle gate passes. |
| `GET` | `/v1/operations/{operation_id}` | durable operation state/result. |
| `GET` | `/v1/operations` | bounded, filterable history. |
| `GET`/`PATCH` | `/v1/configuration` | snapshot/current generation; validated, controlled changes only. |

Representative request and snapshot schemas:

```json
{
  "api_version": "v1",
  "actor": {"user_id": "opaque-bff-attribution", "role": "operator"},
  "slot": 3
}
```

```json
{
  "api_version": "v1",
  "generation": 73,
  "connection_state": "READY",
  "fault_state": "CLEAR",
  "operation": {"operation_id": "UUID", "state": "RUNNING"},
  "firmware": {"protocol_version": 2, "capabilities": {}},
  "machine": {"feed_homed": true, "sort_homed": true},
  "observed_at": "2026-08-10T00:00:00Z"
}
```

| Schema | Required fields | Semantics |
| --- | --- | --- |
| `OperationAccepted` | `operation_id`, `state`, `generation`, `accepted_at`, `status_url` | 202 means admitted or deduplicated; never firmware completion. |
| `Operation` | `operation_id`, `state`, `created_at`, `deadline_at`, `generation` | Durable lifecycle view; terminal form adds `terminal_at`, `outcome` and `trusted_terminal`. |
| `MachineSnapshot` | `generation`, `connection_state`, `fault_state`, `machine`, `observed_at` | Complete immutable reconciliation view. |
| `Error` | `code`, `message`, `request_id`, `generation` when known | Sanitized machine-readable rejection/failure. |

User-visible completion requires `state: SUCCEEDED` and `trusted_terminal: true`.

## Errors and HTTP mapping

| Error code | HTTP | Meaning and client action |
| --- | ---: | --- |
| `VALIDATION_FAILED` | 400 | Correct schema/range/confirmation input. |
| `UNAUTHENTICATED` | 401 | Reauthenticate at SvelteKit boundary. |
| `FORBIDDEN` | 403 | Role/service not permitted. |
| `STALE_GENERATION` | 409 | Fetch snapshot; do not retry prior intent blindly. |
| `IDEMPOTENCY_CONFLICT` | 409 | Same key has different canonical request. |
| `NOT_READY` | 409 | Session/fault/homing precondition is not met. |
| `UNCERTAIN` | 409 | Do not infer state; display recovery workflow. |
| `QUEUE_FULL` | 429 | Bounded admission rejected; retry only with user intent. |
| `DEADLINE_INVALID` | 400 | Deadline missing/out of policy. |
| `DEADLINE_EXPIRED` | 408 | Not dispatched before deadline, or uncertain if sent. |
| `JOURNAL_UNAVAILABLE` | 503 | New motion blocked; operator/service intervention required. |
| `SERVICE_UNAVAILABLE` | 503 | Daemon/socket dependency unavailable. |
| `INTERNAL_ERROR` | 500 | Sanitized failure with `X-Request-ID`; no firmware success implied. |

## SSE

`GET /v1/events` is `text/event-stream`. It accepts standard `Last-Event-ID`; IDs are daemon `event_id`, not protocol `request_id`. Each event uses `id`, `event`, and JSON `data`:

```text
id: 1842
event: operation.progress
data: {"api_version":"v1","event_id":1842,"occurred_at":"2026-08-10T00:00:00Z","generation":73,"type":"operation.progress","operation_id":"UUID","data":{"phase":"sorter_homing"}}

```

Event types include `snapshot.changed`, `operation.accepted`, `operation.progress`, `operation.terminal`, `fault.changed`, `connection.changed`, `journal.fault`, `heartbeat`, and `snapshot.required`. Heartbeats are sent at a configured interval and contain current generation. A cursor older than retained history yields `snapshot.required` with the current generation; BFF must fetch `/v1/snapshot`, replace its model, then reconnect. No event stream guarantees exactly-once browser delivery; operation idempotency and snapshot reconciliation provide correctness. Per-subscriber queues are bounded; overflow is explicit, never silent.

## Versioning and compatibility

The URL major (`/v1`) is the compatibility boundary. Within v1, additive optional fields and new event types are allowed; consumers ignore unknown fields/types. Removing/renaming fields, changing semantics, or altering required fields requires `/v2` and a migration window. OpenAPI schema changes require contract tests, generated TypeScript refresh, a compatibility review and a documented deprecation period. Protocol capability/version negotiation is independent: `/v1` may report a v1 firmware session but cannot claim v2-only fields/actions.
